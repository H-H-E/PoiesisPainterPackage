# ADR 001: Portable score-driven Canvas2D core; evaluate accelerators as optional, measured backends

**Status:** Accepted as the documented v0.1.0 baseline; **no renderer refactor authorized or performed by issue #2**.  
**Decision date:** 2026-11-15.  
**Input:** [pinned reference audits](references/README.md), [parity matrix](parity-matrix.md), [original brief](brief/original-brief.txt), [current implementation](../src/painter.ts).  
**Baseline SHA:** [8665223329eedb138d90e81e1e8254fdc92cc99d](https://github.com/H-H-E/PoiesisPainterPackage/tree/8665223329eedb138d90e81e1e8254fdc92cc99d).

## Decision problem

Poiesis aims for a compact, repeatable, agent-friendly painting vocabulary that creates continuous marks with credible material behavior. Source comparison must not hide five fundamentally different simulation models: p5.brush uses WebGL2 shader-drawn marks and procedural watercolor fills, oil-paint-agents uses CPU oil bristle reservoirs/impasto, washes-js offers CPU watercolor fields with optional WebGL2 simulation, sho uses Canvas2D calligraphic bristle strokes, and wet-edge uses WebGPU wet-sheet physics. None is a legitimate drop-in benchmark for all media or a mandate to copy its renderer.

**Current reality:** `capabilities()` explicitly advertises `canvas2d-cpu`, six preset media, five score operations and a limited local-field simulation. [Painter.render](../src/painter.ts#L62-L182) validates an entire score, uses deterministic per-command seeds, renders each uncached layer into an isolated `MaterialSurface` and `Rasterizer`, then atomically draws the composite to the caller's Canvas. [MaterialSurface](../src/materials.ts#L55-L80) has seven full-size float fields plus one byte tag, 29 bytes per *material-surface pixel*, with optional 4-byte RGBA presentation cache. The final rendering/staging/layer Canvas buffers add further costs; 29 bytes is **not** total process memory. [Painter.render](../src/painter.ts#L124-L152) composites normal/multiply/screen only at the image layer level, not by sharing physics across layers. [Painter.export](../src/painter.ts#L246-L252) rerenders at requested size rather than merely scaling a cached PNG. [v1 score schema](../src/schema.json) is explicitly bounded and validated by [validate.ts](../src/validate.ts). Node rendering uses [@napi-rs/canvas](../scripts/render.mjs), while browser studio uses Canvas2D.

The problem is choosing an *incremental architectural direction* that preserves the score contract and a reliable fallback while allowing better appearance/throughput where verified, without speculative GPU speed numbers or huge complexity for agent prompts.

### Explicit scores and bias

On **baseline correctness, portability, testability and minimal prompt cost**, A beats B–E without requiring unevidenced performance claims. A can render with no GPU adapter, has a bounded schema, and permits byte/pixel tests on a consistent backend. It *does not* meet physically accurate wet-edge/oil-paint-agents parity; that deficit must remain visible. Option D is the least disruptive candidate for UI responsiveness if profiling establishes main-thread blocking. Option B is a candidate only for **specific brush tip/stamp effects** if evidence shows those effects materially improve output. Option C and the full source-engine merger are explicitly deferred: a full rewrite would conflate independent physical models and would not be a bounded improvement.

## Decision and implementation boundaries

1. **Preserve the score/data contract.** Keep [schema v1](../src/schema.json), stable command IDs, material presets, deterministic seeding and validated workload budgets as the single agent interface. New controls require schema versioning, migration/backwards compatibility and separate tests; don't require agents to generate shader source or large point dumps to get basic results.
2. **Use CPU Canvas2D as reference path and fallback.** A future optional backend must accept the same validated score, respect layered compositing and cancellation, report its backend identity and yield repeatable output **within that backend**. Cross-renderer pixel equality is not a baseline assumption because of antialiasing and float differences.
3. **Separate numerical and visual correctness.** Pigment/water mass invariants and monotonic dry behavior belong to unit probes, while color gradients, edge rim, impasto highlights and bristle texture require actual RGBA crops and documented observation. No claim of per-bristle oil physics from visual ribbing alone.
4. **Keep painting state bounded.** Continue dimension, command, expansion and simulation budgets in [validate.ts](../src/validate.ts); dispose scratch canvases and large arrays after each paint; avoid accidental unbounded caches/worker copies or GPU tile retention. Instrument real peak memory and wall time before optimizing.
5. **Maintain a portable raster delivery path.** [Painter.export](../src/painter.ts#L246-L252) returns a CanvasSurface for true-resolution rerender. Native PNG/browser PNG come from consumers. No built-in vector SVG emitter: an SVG of `<path>` objects would not preserve wet-pixel diffusion, raster bristles or impasto relief. Treat SVG score/path export as a *separate* lossy capability with labels, not as proof of faithful painting parity.
6. **Keep agent behavior inspectable.** [Painter.inspect](../src/painter.ts#L232-L235), [serialize](../src/painter.ts#L230), and [crop](../src/painter.ts#L237-L244) reduce what an agent must infer. Future local material sample controls could add adaptive painting feedback without a wet-edge-sized scripting DSL. Do not claim streaming JSONL until the input parser actually supports partial chunks.

## Evidence gates for later alternative work

A backend experiment should be a separate issue with owner-controlled files. Before replacing A, require:

- A public, reproducible fixture for long high-curvature stroke, concave hatch, oil wet-overlap/empty pickup, watercolor contact boundary/evaporation and large region, plus a complex layered composition, with seed and dimensions fixed.
- Same machine/browser/OS and source pins for reference comparison; capture cold/warm run counts, p50/p95 latency, time to first visible result, frame stalls, peak CPU/VRAM memory, output hashes and **actual crop review**. Backend-specific baselines; don't compare original M4/M3 benchmark numbers from source docs to a different host.
- An accessibility/compatibility matrix: Canvas2D no-WebGL path, WebGL2 unavailable/lost context, WebGPU unavailable, reduced-motion controls, keyboard control, mobile constraints, Node/headless exports, and Web Worker availability.
- A net bundle and prompt/score budget assessment: minified/gzip browser core, additional WASM/shader bytes, average command count and tokens per painting, and behavior when a tiny agent supplies invalid input.
- Graceful fallback and no stage-state regression: failed backend init must leave the prior committed image and score intact, with prompt diagnosis instead of corrupt output.

## Short release priorities, derived from real gaps

**P0 (before parity claims):** run `npm ci && npm run check`, real Chromium `npm run test:browser`, native `npm run render` and review exact size/crops. Execute [probes](references/probes.md) across tested hardware and retain logs and hashes. This PR itself changes documentation only, no runtime/tests/CI files.

**P1 (small, evidence-motivated feature requests):** controlled brush reload/wipe (`SH05`/`OA06`), per-point angle/pause (`SH01`/`SH03`), and per-pixel wetness/pigment sensing (`WE05`) address agent expressivity with a bounded interface. Measure quality first. Version any public schema change. Reuse original code, not copy licensed upstream implementation without explicit attribution and review.

**P1/P2 (quality-specific prototypes):** add explicit controllable fill-edge appearance if `PB04` shows it matters, or localized fill pooling if `WA03` tests reveal shortcomings. Prototype WebGL2 stamp shader behind feature detection only for PB01/PB03 with matched fixtures. Explore multi-spectral K/S and shallow-water advection only with data rights, conservation tests, real memory budgets, and a clear user scenario.

**Out of scope:** engine code changes, build/package edits, tests outside owned docs, other workers' issues #3–#6, vendoring upstream, merging, deployment, and release publication.

## Risks, dependencies and reversibility

- **Pixel fidelity vs portability:** a portable Canvas2D implementation is not a physical reference simulator. The parity matrix is the record of missing/approximate features, and changes to material laws must be accompanied by fixture and statistical evidence.
- **Browser/Node divergence:** deterministic scores do not guarantee byte-identical pixels across Canvas2D implementations. Retain backend metadata and separate test expectations.
- **Layer isolation:** crossing physically wet layers currently blends only finished pixels. Inter-layer material mixing requires a deliberate ownership/layer model change, not a cosmetic shader.
- **License and provenance:** MIT permits compliant reuse but requires retaining license and copyright notices. Third-party shader/data/image files may have their own terms; see [notices](../THIRD_PARTY_NOTICES.md). No reference source/asset is imported by this ADR.
- **Rollback:** the decision only documents current architecture and future gates; no production behavior changes. A future accelerator can remain opt-in and be removed without invalidating the source score.
